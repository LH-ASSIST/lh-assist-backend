# 시점 데이터 개선 로드맵

이 문서는 "규정/감사매뉴얼/감사사례가 시점에 맞게 정확히 관리되는가"를 더 실무 수준으로 끌어올리기 위한 개선 계획입니다. **아직 코드로 구현하지 않은 설계 문서**이며, 사이드이펙트가 적은 순서대로 정렬했습니다.

법령·감사매뉴얼 원문을 실제로 어디서 가져와서 어떻게 파싱하는지(법제처 API 연동, LH 문서관리시스템 연동 등 rag-service/적재 스크립트 영역)는 이 문서에서 다루지 않습니다. 백엔드가 그 데이터를 받았을 때 "어떻게 저장하고, 어떻게 조회 안전성을 보장할지"만 다룹니다.

---

## 왜 이 작업이 필요한가

LH가 실제로 공개한 `감사기준 시행세칙`(2025.8.29 개정)을 보면 문서 맨 앞에 이렇게 적혀 있습니다.

```
확 정 일 ： 2025년 8월 29일
시 행 일 ： 2025년 9월 8일
```

**확정일과 시행일 사이에 10일의 텀이 있습니다.** 그런데 지금 `Regulation`/`AuditManual` 엔티티는 `effective_date` 하나만 가지고 있어서, 적재 스크립트가 "확정된 날"과 "시행되는 날" 중 어느 걸 넣어야 하는지 스키마만 봐서는 알 수 없습니다. 실수로 확정일을 넣으면, 아직 시행 전인 규정이 이미 유효한 것처럼 검색됩니다.

또 하나 — 지금 시스템은 "규정 데이터가 갱신되는 중에 분석 요청이 들어오면 어떻게 되는가"에 대한 답을 갖고 있지 않습니다. 짧은 갱신은 우연히 안전하지만(아래 "왜 지금도 어느 정도 안전한가" 참고), 원문을 통째로 재적재하는 대규모 갱신에서는 중간 상태를 볼 위험이 있습니다.

| 순서 | 작업 | 종류 | 기존 동작 영향 |

| 1 | `confirmed_date` 컬럼 추가 (기록용) | 스키마 추가만 | 없음 |

| 3 | ~~데이터 버전(배치) 스위치 구조~~ → 트랜잭션 원자성 계약 문서화로 대체 | 문서화만 (스키마 변경 없음) | 없음 |

## 1단계 — `confirmed_date` 컬럼 추가 (가장 안전)

### 무엇을

`regulations`와 `audit_manuals`에 `confirmed_date DATE`(nullable) 컬럼을 추가합니다. 이 컬럼은 **조회 조건(WHERE)에 절대 쓰지 않습니다** — 순수하게 "언제 확정됐는지"를 기록해두는 감사 추적용 메타데이터입니다. 실제 유효성 판정(`findValidItemIdsAsOf`, `findValidManualItemIdsAsOf`)은 지금처럼 `effective_date`만 봅니다.

```sql
ALTER TABLE regulations ADD COLUMN confirmed_date DATE;
ALTER TABLE audit_manuals ADD COLUMN confirmed_date DATE;
```

### 왜 이 순서가 1번인가

- 컬럼 추가는 nullable이라 기존 행에 영향이 전혀 없습니다.
- 어떤 쿼리도 이 컬럼을 참조하지 않으므로 검색 결과가 1비트도 바뀌지 않습니다.
- 그런데도 가치가 있습니다: "이 규정이 확정된 지 며칠 만에 시행됐는가"를 감사 근거로 남길 수 있고, 나중에 적재 스크립트를 만들 때 확정일과 시행일을 헷갈리지 않도록 스키마 자체가 안내판 역할을 합니다.

`Regulation`에 이미 있는 `amendmentDate`는 이번 조사 전까지 의미가 불명확했고(테스트 코드도 전부 `effectiveDate`와 같은 값을 넣고 있었음), 어떤 쿼리 로직에도 쓰이지 않는 죽은 필드에 가까웠습니다. `confirmed_date`를 새로 추가하면서 `amendmentDate`를 "확정일"의 의미로 재정의할지, 아니면 별도로 둘지는 실제 법제처 API 응답 필드명을 보고 결정하는 게 안전합니다(추측으로 기존 필드를 재활용하면 또 같은 문제가 반복됩니다).

## 2단계 — `effective_date` 의미를 스키마 수준에서 강제

### 무엇을

컬럼 코멘트와 엔티티 Javadoc으로 "이 값은 반드시 시행일이어야 하며 확정일이 아니다"를 명문화합니다.

```sql
COMMENT ON COLUMN regulations.effective_date IS '시행일(확정일 아님) - 이 날짜부터 검색 대상에 포함됨';
COMMENT ON COLUMN audit_manuals.effective_date IS '시행일(확정일 아님) - 이 날짜부터 검색 대상에 포함됨';
```

가능하면 `confirmed_date <= effective_date` CHECK 제약도 함께 겁니다(확정이 시행보다 나중일 수는 없으므로). 단, 기존에 confirmed_date가 항상 NULL이라 이 제약은 아무 행도 거부하지 않습니다 — 여전히 사이드이펙트 없음.

```sql
ALTER TABLE regulations
    ADD CONSTRAINT chk_regulations_confirmed_before_effective
    CHECK (confirmed_date IS NULL OR confirmed_date <= effective_date);

ALTER TABLE audit_manuals
    ADD CONSTRAINT chk_audit_manuals_confirmed_before_effective
    CHECK (confirmed_date IS NULL OR confirmed_date <= effective_date);
```

### 왜 2번인가

1단계 컬럼이 있어야 이 제약을 걸 수 있으므로 순서상 뒤에 옵니다. CHECK 제약도 NULL을 허용하는 조건이라 기존 데이터를 전혀 건드리지 않습니다.

## 3단계 — (수정됨) 버전 스위치 테이블 대신 트랜잭션 원자성 계약

> 최초 설계는 `data_version` 컬럼 + 포인터 테이블이었습니다. 구현 직전에 재검토한 결과 **불필요하게 무거운 설계라고 판단해 방향을 바꿨습니다.** 이유는 아래와 같고, 자세한 검토 과정과 대안 비교는 `/home/jiny/notes`의 자소서 메모에 남겼습니다.

### Postgres가 이미 해결해주는 부분

`rag-service`의 조회 코드(`app/nodes/retrieval.py:155,236,302`)는 매번 `psycopg.connect()`를 새로 열어 쿼리 하나를 실행하고 닫습니다 — **쿼리 하나 = 트랜잭션 하나**입니다. Postgres MVCC는 트랜잭션 원자성을 보장하므로, 갱신 스크립트가 여러 INSERT/UPDATE를 **트랜잭션 하나로 묶어서 커밋**하기만 하면 그 순간 실행 중인 어떤 SELECT도 "일부만 갱신된" 중간 상태를 절대 볼 수 없습니다. 즉 3단계가 막으려던 "갱신 중 중간 상태 노출" 문제는 **스키마 변경 없이, 적재 스크립트를 트랜잭션 하나로 감싸는 것만으로 이미 해결됩니다.**

### 트랜잭션 원자성으로도 못 막는, 진짜 남는 리스크

하나의 문서 분석은 섹션마다 별도 트랜잭션으로 규정을 조회합니다(섹션 1 조회 → ... → 섹션 20 조회). 이 여러 번의 조회 사이에 갱신이 커밋되면, 같은 분석 작업 안에서 앞쪽 섹션은 구버전을, 뒤쪽 섹션은 신버전을 참조하는 **작업 내부 불일치**가 생길 수 있습니다. 이건 버전 포인터로만 막을 수 있는 문제입니다.

### 그런데도 지금 버전 포인터를 만들지 않는 이유

- **확률이 낮습니다**: 실측 개정 빈도(감사기준 시행세칙 16년간 19회 = 평균 10개월에 1번)에 비해, 분석 작업 하나의 소요 시간은 훨씬 짧습니다. 갱신 순간과 분석 작업이 겹칠 확률 자체가 작습니다.
- **겹쳐도 영향이 제한적입니다**: 갱신의 대부분은 미래 시행 예정 규정을 미리 넣는 것이고, 이건 애초에 `baseDate` 필터가 자동으로 걸러주는 안전한 케이스입니다. 진짜 위험한 "이미 활성 상태인 데이터의 소급 수정"은 그중에서도 드문 부분집합입니다.
- **아직 쓸 사람이 없습니다**: 이 인프라를 실제로 사용할 적재 스크립트(법령/감사매뉴얼 갱신 파이프라인)가 지금 하나도 구현돼 있지 않습니다. 소비자가 없는 인프라를 먼저 만드는 건 이번 조사에서 이미 한 번 겪은 실수(적재 경로 없는 감사매뉴얼에 유효성 필터부터 만든 것)와 같은 패턴입니다.

### 대신 하는 것 — 운영 계약 문서화 (스키마 변경 없음)

향후 법령/감사매뉴얼 적재 스크립트를 구현하는 쪽(백엔드든 rag-service든)이 지켜야 할 규칙:

1. 재적재 배치의 모든 INSERT/UPDATE/DELETE를 **하나의 DB 트랜잭션으로 묶어 마지막에 한 번만 커밋**한다. 중간에 커밋을 여러 번 나누지 않는다.
2. 트랜잭션이 너무 오래 걸릴 정도로 큰 배치(수 분 이상)라면, 그때 가서 버전 포인터 방식을 다시 검토한다.

### 에스컬레이션 기준 (언제 다시 버전 포인터를 고려하는가)

아래 중 하나라도 실제로 관측되면 이 절을 다시 열어 버전 포인터 설계를 구현합니다.

- 갱신이 "미래 시행 예정 규정 추가"가 아니라 "이미 활성인 데이터의 소급 수정" 위주로 바뀌는 경우
- 갱신 배치 소요 시간이 길어져(수 분 이상) 분석 작업과 겹칠 확률이 무시할 수 없는 수준이 되는 경우
- 실제 운영에서 "같은 분석 작업 안에서 섹션별로 다른 버전을 참조했다"는 사례가 한 번이라도 확인되는 경우

## 4단계 — AUDIT_ITEM(감사사례) 최신성 가중치

### 왜 REG_ITEM/AUDIT_MANUAL_ITEM과 다르게 다뤄야 하는가

감사사례는 "유효/무효"의 개념이 아닙니다. 오래된 사례라고 폐기되는 게 아니라, 여전히 참고 가치가 있되 최신 사례가 더 신뢰도 높은 참고자료일 뿐입니다. 그래서 REG_ITEM처럼 `WHERE effective_date <= baseDate` 이진 필터를 씌우는 게 아니라, **검색 랭킹에 최신성 가중치를 섞는 방식**이 맞습니다.

### 무엇을

```sql
ALTER TABLE audit_items ADD COLUMN case_date DATE;  -- 사례 발생/작성 시점
```

`retrieval.py`의 `_hybrid_rerank`가 이미 벡터 유사도(`_distance`)와 키워드 점수(`_kw_score`)를 섞어 `_hybrid_score`를 만드는 구조이므로(`app/nodes/retrieval.py:79-111`), 여기에 최신성 점수를 세 번째 축으로 추가하는 게 자연스럽습니다. 예: `recency_score = 1 - (오늘 - case_date) / 최대관찰기간`처럼 정규화해서 가중합.

이건 rag-service 코드 변경이 필요한 영역이라 이 문서에서는 스키마 준비(백엔드 쪽 컬럼 추가)까지만 다루고, 실제 가중치 랭킹 로직은 그쪽 팀과 인터페이스(컬럼명·값 범위)만 맞추는 선에서 그칩니다.

### 왜 4번인가

기존 `AUDIT_ITEM` 조회 경로를 전혀 안 건드리는 **순수 추가 기능**이라 사이드이펙트는 없지만, 3단계(버전 스위치)까지 마친 뒤에 하는 게 자연스럽습니다 — 안 그러면 "언제 적재됐는지"와 "버전이 몇 번인지"가 다시 뒤섞여 같은 종류의 혼란이 반복될 수 있습니다.

## 자소서 문구와의 정합성 (참고)

지금 자소서는 "AI가 올바른 데이터 위에서 동작하도록 설계"라고 결론 내리는데, 이 로드맵을 1~4단계까지 마치면 그 문장이 REG_ITEM 하나가 아니라 **근거 자료 세 종류(REG_ITEM/AUDIT_MANUAL_ITEM/AUDIT_ITEM) 전체**에 대해 참이 됩니다. 지금 상태(REG_ITEM + AUDIT_MANUAL_ITEM만 구현)에서 자소서를 쓴다면 "규정과 내부 감사매뉴얼의 시점 유효성을 통제했다"처럼 범위를 명시하는 게 정확하고, AUDIT_ITEM까지 구현한 뒤에는 "근거 자료 전반"으로 넓혀 써도 됩니다.
